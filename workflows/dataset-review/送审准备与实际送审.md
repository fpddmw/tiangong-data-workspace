# 送审准备与实际送审

主审负责本方获准的正式提交和回执核实。作者提供成熟候选、证据、科学独审处理及保存读回，并承担科学返修。平台第三方负责专家安排和审核裁决。任务是否还包括获准发布或系统使用，取原委派；本页说明提交能力。

## 准备准确提交版

主审接回作者所选的准确正文、必要引用和已有报告。作者与独审已完成的科学判断直接复用；对影响申报用途的实质差额交原作者处理。结构、单位与引用能力见[机器检查](门禁与引用检查.md)，实际写入与读回见[保存与读回](保存与读回.md)。适用性按对象和本次变化判断，使用`work-check --request ID --for handoff`集中读取同一套原检查和回执，不另定义重复验收状态机。

主审确认当前账号、具名送审范围、对象状态、完整读回及提交期间的写责交接。已成熟且获准的对象可以先提交，独立制作继续。CLI 现有 review 的只读预检与操作边界见[实测说明](../../docs/tools/review-preflight.md)。

把本批准确版本和采用依据记在原计划。有待送件的工作日集中处理一次，确实挡住下游交付的成熟件可以提前处理。已有有效授权直接沿用。每批由一名有权操作者按根执行，相关对象核现行写者、状态和授权。关联草稿仍在改、受保护或授权待核时，仅受影响的根留在原计划待办。dry-run 检查可读前提，服务端最终关联范围在写入时决定。已采用草稿交给约定且可读的使用者，原委派含 `submitted` 的范围继续保持送审责任。

## 执行并核真实效果

主审选择已有采用和原生请求。单件和批次共用同一入口，默认预演。

```sh
.venv/bin/python bin/harness.py work-submit-batch --task TASK --adoption ADOPTION --request /ABS/REQUEST.json
.venv/bin/python bin/harness.py work-submit-batch --task TASK --input /ABS/BATCH.json
```

批次文件使用 `{"roots":[{"adoption":"ADOPTION","request":"/ABS/REQUEST.json"}]}`。原生请求含稳定 `requestId`、`expectedActor`、`expectedEnvironment` 和一个准确版本。已有采用中的准确消费者引用会被关联。Source 或 Flow 单独有明确用途时，可在同次选择用 `--use L7-L9` 或根的 `"use":"L7-L9"` 指向原采用的用途段落。选择与原用途一并归档。

用原 `dataset.review_submission` 授权确定 `submit` 或 `resubmit`、准确 `type/UUID/version`、账号、项目、具名操作者及允许联送的对象。缺授权时，沿 `work-decision-record --decision` 引用真正的具名授权。决定的 `scope` 含 `task`、`object`、`action`、`account`、`project`，`statement` 为 `allow`，`details` 含 `operator` 和 `authorized_related`。采用、准确正文和原生请求已经在本次选择中引用。

预演列出原请求的账号、选择方式、现有具名决定、正文可见引用和该采用的在途作者尝试。引用是核查线索，最终联送范围以服务受理后的效果和状态读回为准。CLI 0.4.5 无法在提交时把实际范围限制为一个对象或精确清单。原决定有这种限制时保留待送项，沿 [CLI #548](https://github.com/tiangong-lca/cli/issues/548) 跟踪。

原书面委派允许主审选择平台联送时，由原主审在现有决定中明确接受服务端在提交时确定最终范围。该决定的 `details` 增加 `"related_policy":"native_business_related"`、原 `adoption_id` 和带哈希的 `request_ref`，`authorized_related` 填空数组，以示授权方式已经变更。原生请求须选择联送，原本要求单件的输入保持原样。主审若决定变更方式，用新请求明确选择联送。持该决定的具名操作者加 `--execute`，逐根复核停止、在途和未知尝试、账号、精确正文和已知引用。受理后读回审核号及实际变更。出现预料之外的变更时，保留审核和读回证据，暂停同一账号和项目下无法确认与之无关的后续根。父包承诺的 submitted 以实际受理为准。

本机已实测作者 OAuth 的本人列表和精确审核读取。受管送审通过上述入口执行，实际 `review submit/resubmit` 由宿主逐根调用。使用 Platform 时，先核界面可能触发的正文保存、Model 计算或成组保存和相应授权。需要其他有权者操作时，交清准确动作并接回结果。[当前服务边界](../../docs/tools/review-preflight.md)

逐根保留原请求、审核号、受影响身份及提交后的正文与状态读回，核实实际变化。已有审核号用 `review get --id` 读取。原提交效果为 `unknown` 时，核原私有账本关联、同账号、同环境和完整原请求，具备这些条件时沿同一原输入查询回执。查无可信结果继续保留 `unknown`，其共享依赖待查，互不影响的根可以继续。原账本缺失时，同一命令可能进入初次提交路径，应沿原平台记录和可归属的只读证据查证。

## 提交后的责任

主审核实提交回执后继续原目标余项。`work-show` 列出本根审核号、准确审核读回、原采用和原作者请求。平台待分配、待审核及意见变更由用户指定的[轮询维护者](../../roles/platform-feedback.md)据此跟踪并定期汇总。需要修改在审正文时，原写者依据实际退回、可编辑状态和相应授权操作。意见及状态的读取见[原生审核](../business-flow/native-review.md)。

submitted终点取本方实际提交回执/准确状态读回；发布另取具名授权与实际发布读回。部分成熟成果可阶段交付，主审继续整包全部余项；原任务的`work-complete`按当前全范围检查，pending后补齐可用同一说明重试，不靠换文件名解锁。

用原采用时间和实际审核回执核成熟草稿等多久才送出。确有因过早提交、正文不一致或关联越界需要退回的，保留原审核号和具体差异。平台新提出的科学意见沿原审核记录组织作者返修。原审核结束后仍需核准确版本的可编辑状态与其他活动审核。
