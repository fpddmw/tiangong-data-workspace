# LCA 数据库业务与协作 Design Book

版本：0.3 实施基准 · 日期：2026-10-29 · 状态：已批准在独立功能分支实施；尚未部署。

修订基准为 data-workspace 的 [v0.1 原文，提交 695eb4b2](https://github.com/fpddmw/tiangong-data-workspace/blob/main/docs/data/lca-database-design-book.md)。本稿重组原有十二章，将数据研制、送审、评审返修和发布放入稳定任务责任之中，统一说明知识复用、共享维护与上游改进。现有科学要求、专业对象、原生任务与操作证据继续保留。

这份设计服务于持续的 LCA 数据库建设：发现有价值的缺口，组织完整任务，取得可使用且可追溯的成果，并让真实使用中发现的问题改善后续工作。可靠性同时体现为科学质量、任务方向、实际可用性、交接成本和推进效率。不同模型应遵守相同的事实、证据与操作约束；科学判断的分歧应能追溯到用途、证据和假设。

用户已批准按本版蓝图拉取 data-workspace 并在独立分支重构源码。文中“应”“负责”描述目标工作方式；源码检查、宿主接入、部署和真实使用分别核实。生产数据库、账号权限、自动化和在途任务保持原状态；本书不授权接管原写者、启用轮询或修改线上数据。

## 1. 数据库目标与完整任务形成

### 1.1 从数据库需要形成可持续负责的任务

总主从数据库覆盖、真实使用需求、已知科学问题、评审意见和共享依赖中发现工作。接续时先读现有任务的贡献、未决依赖和反馈变化，再沿数据库已有检索、统计、包索引及专业报告查相关范围。现有记录不足以支持缺口判断时，先安排有边界的调查；缺口线索、已核实缺口与已决定开展的任务分别表达，不将一次空查询直接变成批量建库任务。

每项独立任务应有可说明的背景、用途、范围和预期贡献，并由一位任务负责人持续承接。总主在原任务 brief／计划中说明该任务服务的数据库用途、当前依据、关键未知、允许自主调整的范围及需要交回的取舍。已有任务能够承接的增量直接回原负责人；确需独立目标与上下文时才另立任务。负责人在这一背景下规划、安排执行、判断进展和调整路线。

任务可以是完整数据工作包、一组有共同用途和判断背景的数据修订、系统建模与计算，或具有明确边界的缺口调查。拆分依据是需要共同理解的科学关系和依赖，以及上下文能否独立管理。材料名称、Process 数量、目录、单篇文献和 worker 数量不自动决定任务边界。

完整任务与原生执行工作包可以有包含关系。工作包可含一个或多个 Process 及必要支撑对象，继续沿原 Task/attempt 工作。Flow、Source、Contact、一个缺失字段或一次工具调用不默认各建一项业务任务。共享供方和共享研究由明确的原任务承担，其他消费者引用同一成果与版本。已有原生关系能表达归属时直接复用，不为体现层级再建同义记录。

身份或方法尚未查清时，任务可以保留研究问题和待确定接口。负责人先安排必要调查，再据证据收敛对象、方法和交付；不得为满足登记要求先造 UUID、数量或确定结论。

### 1.2 发现与排序依据

总主先排除范围外、重复、已经有人处理，以及证据不足以支持所提动作的事项。缺供方时，先核流的含义、同义身份、单位、可见性和实际选供关系；查询空结果不等于数据库不存在，基本流没有供方 Process 也不自动构成缺项。

优先处理影响原目标的科学错误、明确返修和关键用途缺口，其次考虑阻塞多个必要消费者的共享依赖，以及能够明显减少重要决策不确定性的工作。同等重要性下，输入充分、可以执行或接近可用交付的任务优先。局部阻碍只约束其真实依赖，不阻塞无关任务。

排序保留影响对象、证据和取舍理由。缺少可信影响量时保留未知，不编造碳贡献比例或统一分数。容易完成的低价值工作不能持续挤占关键任务。总主说明做什么、为什么值得做；任务负责人根据完整背景决定具体怎样推进。

在管任务数与同时运行数分别考虑。负责人按输入就绪、共享写责、可用运行资源和待审负荷安排执行，审查积压时先处理会阻塞采用的返回，再开新的独立工作；能共用背景与判断的成果可合并安排审查。总主调整任务间的资源和优先级，不按材料或 worker 数量机械增设主审。普通查询与已有记录足以支持安排时，沿当前入口处理，不为并发管理另造打分系统。

### 1.3 贯穿任务的三个循环

同一任务及其当前计划承接三个相互连接的循环：

- **研究与生产：**发现缺口、规划、研制、必要检查、实际使用或送审交付。
- **外部反馈：**取得意见和状态变化、对齐版本、作出判断、回复或返修、核实发布及用途。
- **共享改进：**发现重复阻力、集中诊断、上游修复或方法更新、版本采用、后续效果反馈。

任务负责人持续掌握前两个循环的科学背景；维护者承接第三个循环的共享责任。进入下一业务阶段不默认更换负责人，也不要求把全部背景重新交给另一位 Agent。

研制送审、正式发布与整个任务完成分别有依据。实际进入 20 并完成适用的三专家分配，可以完成声明的研制送审阶段；完整 LCI、系统计算、公共数据替换或其他整体用途仍按原任务核验。子过程交付不能提前关闭父任务。

## 2. 四类职责与持续责任

### 2.1 职责、会话和专业能力

| 职责 | 持续承担的工作 | 决定与交回边界 |
| --- | --- | --- |
| 总主 | 理解数据库需要，形成完整任务，安排优先级与资源，消费任务贡献和跨任务问题 | 在既定授权内调整整体安排；重大用途、预算、权限和路线变化交用户；不默认逐包复审 |
| 任务负责人／任务主审 | 掌握原目标、背景、当前认识和边界；规划、派发、核进展、判断用途、安排审查与返修 | 自主处理范围内计划和接续；跨任务取舍交总主，共享问题交维护者；不常态化重做计算 |
| 执行者 | 连续完成范围明确的调研、数据、模型、计算、操作或独立检查，进行必要自查并返回准确成果 | 沿原任务、专业合同和授权实施；偏离范围或重要未知交负责人；不自行修改共享规则 |
| 维护者 | 集中分诊共享问题，识别机制与上游归属，组织 Issue、修复、工程审阅、版本更新和效果核实 | 沿具体委派处理维护；科学用途留任务负责人；正式规则、权限和重大路线变化按影响审阅 |

四类职责不固定为四个进程、四种模型或四个账号，也不意味着每项工作必须依次经过四位 Agent。总主、任务负责人和维护者使用有明确责任的持久原生会话，执行者沿原派发接续。Data、Calculator、数据编辑和工程修复作为专业能力。独立审查固定由负责人派出的临时审查子 agent 完成，属于执行职责，不新增第五类常驻角色；不得由作者或任务负责人自己代替该独立检查。

原 v0.1 的业务能力全部保留：TO DO 的整体发现归总主、任务内发现归负责人；Plan 归任务负责人；data-editor 由执行者承担；review-feedback 的采集由有限程序作业完成，科学处置回原负责人，获准的平台动作交实际有权执行者。共享维护由维护者贯穿这些业务，而非再次回到科研协调入口。

### 2.2 任务主审的深度与推进责任

任务主审持续核对原计划与 worker 的实际进展，判断成果是否覆盖所派用途、边界是否漂移、重要未知是否改变，以及下一步投入是否合理。它应识别工作被拆成无意义小动作、局部技术问题扩大为全局阻塞、长期深挖低收益细节等偏离，并调整安排。

计算和专业细节首先由执行者、专业工具及必要的独立科学检查承担。任务主审读取与决定有关的含义、差异、专业检查覆盖和限制，不默认逐行验算、重读全部原文或重做 worker 的推导。已有合格且未变的依据继续复用。

关键数量矛盾、决定性假设缺证、边界变化、检查冲突或高影响异常构成深入检查的理由。负责人明确争点和影响，向审查子 agent 交付具体核查问题，读取其证据与结论后决定任务接续。负责人可以查看关键依据以理解问题，但不接管整套技术细审。它仍对用途判断和接续负责，不能仅见到 PASS、accepted 或文件齐全就采用；也不能用反复重算替代对计划与实际增量的判断。

范围内的执行顺序、补证、普通返修、适用现成方法和有限用途采用，由任务负责人依据原计划与有效检查自行决定。改变原用途、关键科学假设、重要验收标准，或影响其他任务的资源与共享选择时，负责人将具体取舍交总主；超出总主既有授权的再交用户。一次局部缺项不自动逐级升级，原计划已有明确办法时直接承接。

总主消费任务级贡献、关键限制和例外。新用途、跨任务冲突或异常证据需要复核时，应指出具体对象及影响范围，避免对已处理成果再作一遍默认逐项审查。

### 2.3 会话职责与运行配置

优先复用已有目标、原生会话绑定及正常工具入口，保持准确任务与实际负责者的关联。角色名称用于理解职责，不赋予账号权限，也不代替原生 actor、原写者或操作授权。每项精确对象仍只有一个实际写者；任务管理责任与对象写责分别确认。

总主在获准的派发范围内建立或复用任务负责人的持久会话，任务负责人继续派发和接续执行工作。一个执行者连续完成已派工作，普通补证回原执行者。需要跨轮持续工作的执行包复用独立执行会话；有界执行和独立审查优先使用宿主原生子 agent。首次独审新建非作者的独立上下文；返修优先接续原审查子 agent。跨宿主的独立审查仍是由负责人创建、限定输入并接回结果的子任务，不新增用户侧常驻审核角色。

模型和宿主按职责配置，执行者、科学审查子 agent、任务主审、总主及维护执行可以采用不同组合。“子 agent”表示派发与返回关系，不表示继承 worker 的模型。当前拟优先核实 ds4.1flash + Claude Code harness 承担实际 worker，GPT 的 SOTA 模型承担总主及科学主审；这是待接入方向，具体模型标识、提供方兼容性、权限和调用能力尚待核实。独审和工程执行分别配置，不以本书写死型号或某个宿主 API。

复用部署已有配置，按职责选择实际模型、宿主、工作位置及可用工具。运行记录自动带上实际模型标识、宿主会话／运行身份和配置版本；“SOTA”不作为自动追随最新模型的运行指令。更换模型、宿主或账号时沿原任务在合适接续点调整，不静默替换在途运行。已有执行会话继续遵守其当前契约；本稿不修改现有 Sol 执行安排。

执行者直接完成所派工作，不自行递归分派或找另一位作者互审。任务负责人和维护者负责各自范围的执行及审查派发。用户可以进入原任务纠正、查看依据或暂停有关工作。当前仍由用户发起主会话接续；执行者和维护者不主动发消息或唤醒主会话，既有暂停继续有效。子 agent 对创建者的原生完成返回按原派发承接，不另调用跨会话发消息工具。

### 2.4 派发、返回与跨宿主接续

派发由负责人调用原任务的管理入口发起。入口读取原任务、当前计划与授权、输入版本和已有运行，先判断应接续原执行还是启动新执行。总主派任务负责人，任务负责人派研究执行与科学独审，维护者派获准工程执行与工程预审。普通执行者只交回结果与需要处理的事项。

同宿主优先调用已有创建、接续、等待、停止和结果读取能力；跨宿主优先调用目标宿主已有的非交互启动、会话恢复和结果输出入口。所需适配补在原 CLI 或宿主集成处，职责限于传入任务引用、启动或恢复运行、取得身份及结果、映射回原请求；不再建立一套研究调度器。具体 API 或命令在接入时核定，不能把一个宿主的子 agent 调用当成可启动任意其他宿主和模型。

一次派发沿原请求保留启动意图，取得实际会话／运行身份后绑定。启动返回丢失时，先沿该请求、目标宿主运行与输出记录核实是否已启动；无法确定则保留“启动结果未知”，由原派发者处理，不盲目再起相同工作。恢复沿原会话和已知成果接续；需要新执行上下文时仍关联原任务与本次交接，不另造业务身份。

负责人向执行者提供原目标、当前边界、所派工作、准确输入与必要方法入口，并说明返回位置及需要交回的判断。首次接手和实质交接展开相关背景，正常接续只补变化。宿主、模型和工具设置从所选配置取得，任务正文不反复填写环境参数。实际接入先核必要材料、专业工具和返回入口可达；同一配置与访问范围未变时复用已核结果，具体失败再核有关部分。

SQLite 在其所属运行环境中通过现有管理 CLI 读写。共享环境中的不同宿主复用原路径；跨主机访问复用获准的既有远程执行连接，在数据所在主机调用同一入口，并返回有界查询结果和原件引用。原始材料按其原访问范围读取，宿主看不到的路径不能作为已交付输入；缺少可用访问方式时指出具体缺口，先不派依赖该资料的工作。不复制一份可写主库，不让远端进程直接跨网络打开 SQLite 文件，也不因接入自动迁移科研资料、传递凭证或新增服务。

执行结果先保存到原工作位置。子 agent 的原生完成返回，或独立执行会话的结果读取，由接回入口关联原任务、请求、实际作者与准确成果。宿主有结束事件时复用；无事件时，由获准的有限查询或负责人下次接续读取原运行。当前不新增后台常驻轮询或主会话唤醒。退出码、最终聊天和文件存在分别只是运行证据；第3.2节的返回保存成功后，当前视图才显示已交回；科学采用仍由负责人作出决定。

接回失败时保留原运行与成果位置，恢复后重读同一次返回，不能重跑研究来补一条管理记录。跨宿主暂不支持某项创建、恢复、停止或读取能力时，将该具体动作列为接入缺口；不能把缺失动作写成“已自动完成”。

## 3. 任务入口、计划与四类事项

### 3.1 从准确任务直接恢复当前工作

日常入口复用原 CLI 的任务列表、任务详情和相关对象读取，按实际负责会话与任务绑定生成当前视图。总主先看任务贡献、待处理例外和跨任务依赖；任务负责人读取自己的原目标、当前计划、有效成果、未处理返回与意见、在途运行及下一步；执行者按已派范围恢复原输入、专业检查点和剩余工作。各角色读取同一事实，不各维护一份总表。

已有可信任务绑定时直接恢复；没有绑定或存在歧义时先选择原任务，不加载全库或另建替代任务。当前入口先显示有实质变化或尚未处理的部分，并保留完整背景和历史的展开入口。内容从原记录组合，含足够判断用途与下一步的实质摘要，不能只有文件名。

稳定背景由原 brief／计划唯一维护。日常返回交新增成果、重要差异及待决定问题；首次接手、真实换人、故障恢复或用途变化时，恢复原目标和当前认识、有效成果与限制、未决决定、在途副作用及最近变化。执行者在动手前核所派范围与实际输入是否一致，发现冲突回原责任人，已有明确纠正优先。这里规定读取内容，不要求每次另写恢复报告。

原生会话压缩或终止不改变业务责任。能恢复原运行时沿原身份接续；必须新建上下文时，负责人从同一入口取得上述材料并明确交接，记录替代的会话关联。旧会话和成果保留历史，未结束操作按第7.2节核实后再安排。已处理的返回退出待审，长期研究继续与本次审阅结清分别表达；新版本或新用途只复核受影响决定。

### 3.2 每类事实的唯一维护位置

| 内容 | 维护位置与责任 | 当前入口如何使用 |
| --- | --- | --- |
| 原目标、科学背景、重要选择和路线 | 原任务 brief／计划，由总主或任务负责人维护 | 读取当前理解，历史按需展开 |
| Task、attempt、检查、计算、保存和平台操作事实 | 原生工具、原写者及平台记录 | 引用准确身份、版本、覆盖和观察时点 |
| 来源、完整候选、模型、计算与科学解释 | 原科学包及专业对象 | 保留原件，按争点展开 |
| 对成果或评审意见的实际处置 | 原审阅／意见记录，由合格实际处理者保存 | 关联本次成果、用途及未决条件，驱动接续 |
| 管理责任、优先级和必要跨任务关系 | 优先使用已有关系；缺失部分进入同一管理存储 | 按准确任务和 actor 查询 |
| 上游诊断、修复、审阅与发布 | 对应 Issue／PR／MR／发布记录 | 本地引用上游身份，保留受影响任务和采用情况 |
| 方法和 Skill 正文 | 原方法、工作流、Skill 或代码 | 索引现行版本、条件、实际使用与替代关系 |

管理事实采用 data-workspace 既有 SQLite 管理库，经现有 CLI 补足任务责任、请求与决定的必要关联，当前视图由查询端生成。已有原生状态直接经原读取入口取得，不复制一套竞争的 accepted、owner 或运行游标。以下“接回”“处置”是待接入现有 CLI 的逻辑动作，具体命令名、表和字段映射需核源码与运行端，不表示现有接口已经全部支持。

接回入口从实际派发取得任务、请求、作者及运行身份，从成果与原生报告取得准确版本和引用。先核原件已保存且可读取，再将本次返回及其关联写入原记录；重复取得同一次、同一版本返回时复用原记录，内容改变则保留新的返回版本。模型正文只能提供自己的判断，不能自报一个身份覆盖真实作者，也不能把“检查通过”变成伪造的 A07 或平台回执。独审结果经专业合同允许的入口核身份、覆盖及版本后承接；尚缺对应适配时保留专业意见，明确回执未接通。

任务负责人沿原审核请求提交本次用途决定，引用准确返回、适用独审与专业依据，说明采用、返修或具体待决条件。同一管理事务保存该决定及必要的待办关联，当前视图读取其结果：已处置部分结清，返修留在原任务，仍待决定的部分保留；不因项目继续而把已审返回永久挂起，也不因局部采用而关闭未覆盖范围。复杂部分沿原包成员关联，无需每个字段再建一条事项。

成果文件、宿主返回、平台操作与管理数据库不共享一个事务。管理提交失败时，原成果及回执继续有效，接回入口重试同一次登记；科学决定提交失败时保留待处理，不把未保存决定显示为已采用。未知平台动作先查原 attempt 的实际结果，不能重发动作补记录。原数据和原管理提交成功后，生成页失败只重建视图。恢复直接沿原请求及回执进行，不新增一套手写失败台账。

看板由上述读取入口生成，work/lca-production/board.json 若保留则只作导出，不接受 Agent 手工修改来改变任务事实。原子认领在有权维护责任的原记录上按 revision 比较并提交，冲突后重新读取，不能把 Git 同步当作并发互斥。新增管理关系通过同一 CLI 适配增补原 SQLite，不另建可写看板库。

### 3.3 计划保存判断，动态事实引用原记录

公共计划承接以下问题，按任务复杂度展开：

- 要支持什么用途，本轮交付到哪里，哪些整体要求仍在原任务中继续。
- 产品或服务、reference flow、过程结构、关键依赖，以及复用、修订或新建的理由。
- 采用什么证据与计算方法，哪些假设和未知影响用途，怎样取得足够依据。
- 当前认识、下一步价值，以及新证据出现后怎样继续、调整或结束。

当前底稿、准确对象与方法版本、原 Task/attempt、检查报告、意见处置、保存读回及发布回执直接引用相应记录，不在计划、看板和交接报告中重复抄写。工具能提供的身份与事实自动取得；负责人只维护需要判断的内容。简单工作用短计划，未适用的复杂区块不强制填写；影响当前决定的未知则必须明确。

优先复用原 brief；确需独立计划时仍留原包，该正文是目标与路线判断的唯一维护源。管理库关联其准确版本，并保存必要的责任、执行和处置事实；当前视图读取正文与这些原事实，不另存一套需要手工同步的计划全文。产品定义、重要假设、来源粒度、依赖或验收缺口实质变化时，由负责人修订原计划并更新引用，说明新证据改变了什么决定；普通轮询或相同证据重读无需改版。旧冻结版本继续保留。

### 3.4 四类事项沿原记录衔接

| 事项 | 谁提出／发现 | 谁处理 | 处理后回到哪里 |
| --- | --- | --- | --- |
| 后续工作计划 | 总主、任务负责人 | 对应范围的负责人 | 原任务计划与原生工作安排 |
| 提交审核请求 | 执行者随准确成果返回 | 任务负责人判断本次独审需要与范围，派出或接续审查子 agent | 子 agent 专业意见与负责人任务处置分别关联原请求 |
| 缺陷发现处理请求 | 执行、审阅或实际使用者 | 维护者诊断共享问题；任务负责人判断科学影响 | 原维护事项、上游关联及原任务采用 |
| 外部评审反馈处置 | 原评审平台，经每日有限程序采集 | 原任务负责人作科学判断，实际有权执行者落实获准动作 | 回复、原任务修订、等待或发布核验 |

四类事项表达不同责任，不增加四张表单。已有返回、评审或工程记录可以承接时直接使用。普通发现不自动变成改进项目；科研采用、工程修复和平台审核有各自依据。

### 3.5 送审工作包的四态视图

以下四态只描述声明了送审与发布交付的数据工作包。完整研究、系统计算和维护任务沿各自目标判断，不强制以 published 为共同终点。

| status | 含义与进入依据 |
| --- | --- |
| pending | 已纳入范围，等待计划或重新安排；已有依据且尚未被领取，或已具备返回修订的条件 |
| working | 已由有权负责者原子领取，正在计划、研制、检查、保存或准备送审 |
| reviewing | 必要送审对象实际为 20，有对应 review，且适用审核单元已分配三名不同的合格专家 |
| published | 本工作包声明范围的真实发布、完整读回及适用的替换／引用关系已验收 |

四态与平台 state_code 分开。已到 20 但专家分配未齐仍为 working，并显示真实平台事实及待办；审核通过而未发布仍为 reviewing。部分对象成功时保留逐成员结果，按声明的必要范围判定工作包。

pending → working 读取最新 revision、核原写责并原子认领，竞争失败者重新读取。working → reviewing 消费本轮完整送审及分配证据。reviewing → pending 需要有据返修决定、适用的实际退回和可编辑状态；此前可以形成待办或只读返修预案，尚不启动写入。reviewing → published 核实际批准、发布及本包验收。published 后的新修订沿原任务增加适用 cycle，保留旧发布事实，编辑对象按后继草稿规则确定。

等待、暂停、取消、被替代和故障保留真实阶段，并表达原因、恢复条件和是否允许派发，退出不适用的活动视图。它们不伪标 published，也不靠超时自动恢复或接管。澄清、重复意见、换模型或换会话不自动新开 cycle。

拟议接口只承接已有 task 身份与版本、原请求与范围、优先理由、对象及依赖、计划引用、负责者与 native_refs、下一动作、暂停条件、review／送审／发布回执和观察时点。部署时逐项确定来源，已有字段直接映射，不要求执行者重新填写整包。字段名称不构成现有 Foundry／CLI 已支持的参数。

## 4. 数据研制、系统使用与正式送审

### 4.1 用途、reference flow 与过程结构

研制沿“用途与交付边界 → reference flow → 过程结构 → 复用／修订／新建 → 证据与计算方法 → 工作及验收”推进。任务负责人掌握重要选择，执行者在约定范围形成完整方案与候选。

reference flow 明确产品、能源、服务或废物处理功能，规格与物理状态、参考属性、数量、单位、方向及时间、地域、技术代表性。处理废物的服务可能以待处理废物输入为参考，不能机械套用产品输出。功能单位、参考量及过程缩放关系按实际用途表达，单位换算保持来源与物理意义。

每个拟议 unit process 明确活动、边界、参考交换、缩放、上下游连接、共产品和分配，以及现有身份选择。过程数由物理活动、数据粒度、复用价值和用途决定，不按字段数或缺项数拆分。未知量先保留并安排研究，取得证据后修订计划。

多过程任务区分真实前置与可并行工作，共享供方保持原写者。循环依赖按同一系统问题分析。完整上游网络和完整 LCI 不自动成为每个独立过程启动的前置条件；系统型交付仍须验证实际采用、连接、覆盖和计算结果。

Model 派生的 Process 从原单元过程、模型连接和目标量修订后重新生成，不能直接手改派生交换凑结果。计算范围、方法、运行权限和背景代理沿原合同及项目科学要求核实。

### 4.2 当前底稿与完整候选

执行前定位线上完整正文、最近完整读回及已接受但未保存的候选，比较三者差异，选定本轮底稿。绑定对象版本、相关依赖、观察时间、原 Task/attempt、原写者、真实平台状态和适用权限。已有接受体不能被一次最新读取或旧草稿静默覆盖。

执行者收集来源，完成数量、单位、过程连接、共产品处理和方法说明，形成支持本轮用途的完整候选。来源事实、派生计算、固定估计、模型选择和未知分开表达，保留原件精确位置、计算关系和假设依据。年度量等要求沿现行数据原则及已确定的项目办法处理，不留给模型逐对象随意选择。

资料不足时，适用且有依据的估计披露假设与限制；影响正式用途的关键未知保留为未完成及具体补证。可供有限用途使用的成果明确条件。已有办法在适用范围内复用，新的处理方向或重要用途变化交相应负责人判断。

### 4.3 独立审查使用临时子 agent

作者先消化机器报告、完成自查，将准确候选与审核请求交回。原专业合同要求独审（包括适用的 A07）、重要科学争议或有影响的专业异常时，由任务负责人派出临时审查子 agent。普通进展同步不启动独审；每个字段、交换或工具步骤也不单独启动。角色独立与必要检查保持明确，具体模型、宿主及调用名沿第2.3—2.4节配置。

独审按以下方式执行：

1. **确定范围并创建。** 负责人依据本次用途、专业合同、候选变化及已有有效检查，提出需要回答的科学问题、必须覆盖的对象和受影响依赖。专业合同要求完整包审查时保持完整覆盖；已有审查后的局部修订按实质影响复核。负责人通过所选宿主的原生子 agent 能力，或按同一派发关系接入的独立运行入口，建立非作者审查上下文。作者自查、负责人自己的判断和作者切换角色提示均不替代独审；不固定某个模型或 API。
2. **输入。** 提供用途和边界、准确候选与依赖版本、来源和计算入口、作者自查及机器报告、已有有效审查、待查争点和应完成范围。稳定背景引用原计划，证据沿原包读取，不复制作者完整聊天和全部日志。作者结论是待核主张，审查者必须能够直接取得与判断有关的原始证据。独立上下文减少对作者推理的依赖，不隔离必要背景和既有反证。
3. **执行。** 子 agent 以只读权限配置运行；宿主支持时按该配置限制工具，尚无技术隔离时明确其限制，不将任务提示冒充权限控制。它使用原件、已有只读检查和必要的无外部副作用核算，检查产品语义、数量基准、来源适配、边界、分配与物料／能量关系；不修改被审数据、共享规则或平台，不替作者返修，不再分派。已有检查证据按版本和适用范围复用。发现范围外的高影响问题时，定位证据和可能影响交回负责人，由负责人决定是否扩审或另安排工作；普通措辞和低影响细节不自行扩成全包重算。必要证据不可达时返回具体缺口。
4. **返回。** 子 agent 通过本次派发的完成返回交回检查范围、准确版本、影响用途的问题、原件位置、未决条件及专业意见。第3.2节接回入口关联真实审查身份、原请求与成果，按专业合同支持的合法语义保存，避免再手写一份相同审核报告。不向总主另发消息；宿主返回和专业回执适配未接通时如实保留缺口。
5. **处置。** 任务负责人核意见是否回应原用途、计划与应查范围，作出采用、具体返修或等待决定，并处理扩审建议。技术争点不清时向原审查子 agent 追问具体依据；确需第二意见时只派实际争点，不默认再审全包。关键分歧未解决时保留未决状态，不能为推进改成通过。总主消费任务贡献，不默认重复专业审查；平台专家审核仍按其制度执行。
6. **返修与接续。** 原作者实施修改，返回新版本及差异。负责人优先接续原审查子 agent 检查受影响部分；原上下文不可恢复时，新建审查子 agent 并提供原用途、有效审查及本次差异。审查发现的新增风险可以扩大受影响范围，扩大的原因需说明；已核未变证据继续使用，不能仅因更换会话或模型要求重做。

结构 PASS、局部 accepted 或有限草稿可保留，均不自动形成完整科学合格或正式送审资格。A07 适用性与合格回执仍沿原合同核定，子 agent 的身份本身不保证结论正确。新增 Flow／Source 语义随完整包审查；科学分歧定位到实际争点，避免仅凭措辞差异反复全包审核。

### 4.4 保存、完整读回与送审

保存前核当次身份、所有权、平台状态、前像、原生合同和有效检查，依赖按适用要求保存。保存后比对完整正文、准确版本、状态、所有权及关系。未知结果沿原 attempt 恢复，成组操作保留逐成员成功、失败和 UNKNOWN，不整批重放。

正式送审实际提交并核对 20 与对应 review。原 B08/B09 表达同一次提交的逻辑阶段，不能据两个节点编码发出两次提交。原生入口不能逐节点拦截的操作，需要在动作前完成适用的等价检查，动作后完整核验，不声称拥有未部署的逐节点保护。

适用的研制送审终点还要求三名不同、合格且有效的专家分配及读回。专家按平台真实审核单元绑定；一单元覆盖多个对象时列明成员并引用同一有效分配。三条记录对应同一人、历史 review 分配、已退出或失效分配、利益冲突均不能算作本轮三名合格专家。实际审核制度与资格查询能力在部署时核实。

提交成功而分配失败时，保留真实 20 和已有分配，继续原 review 的分配动作，不重新送审。作者操作、专家分配、退回、批准和发布由具备对应权限的账号经支持入口执行，角色名称不授予权限。已有明确授权覆盖的常规动作直接推进，缺少权限则指出具体动作与责任方。

### 4.5 冻结交付与系统用途

冻结送审包引用接受的完整正文、相关依赖、计划版本、来源、假设、计算、必要检查和独审、原生回执、review、专家分配及剩余限制。原件留原位置，包索引用准确引用组装，避免复制整套日志和文献。正常负责人已掌握的稳定背景不重复搬运；必要时可展开完整依据。

正式发布沿实际流程核目标范围、批准和发布记录、读回及适用的公开版本替换、引用或下载验收。发布之后仍按原用途判断任务完成。完整模型或 LCI 交付另核组件、Flow／供方连接、选定版本与方法、原 job 和输入、覆盖与残余边界，以及同源计算结果。平台对象存在、一个求解成功或子任务结束不能独自证明系统交付。

## 5. 科学审阅、外部反馈与持续接续

### 5.1 一次专业决定被后续直接使用

执行者交回准确成果、实质变化和影响用途的问题。任务负责人核计划与实际、专业检查覆盖、限制和下一步，以采用、具体返修或保留明确未决事项结束本次处理。合格的科学决定经第3.2节处置入口沿原记录保存一次，供采用、待办和总览使用；已经结清的返回不因项目仍在进行而永久待审。工具问题另由第6章的原维护事项承接，科研通过不自动结清工程问题。

内部独立科学检查由第4.3节的临时子 agent 完成，任务级用途决定由任务负责人作出，平台专家意见和正式审批沿平台责任处理。已有适用的子 agent 检查可以直接消费；新增变化、独立性问题或重要争议需要补充检查时，由负责人接续或新建审查子 agent。负责人自己查看依据或作任务决定不记为独审。总主不默认再审所有数据，维护者不重复裁定科学用途。接续入口同时保留实际作者、审查子 agent 身份、输入版本、覆盖及未决条件。

负责人读取原始关键证据用于理解范围和处置，详细计算核查交审查子 agent。子 agent 必须能够沿引用读取必要原件；只有上一位模型结论而无足够证据的摘要不能支撑关键判断。检查强度以用途和实际疑点决定，堆入全部计算日志和文献不能代替明确审查问题。

### 5.2 定时采集与事项处理分开

送审反馈由现有调度入口每天调用一次有限采集命令：从原记录选择纳入范围的 review，调用受支持读取接口，比较意见及状态版本，将变化写回原意见记录，更新可靠采集位置后退出。已有 CLI 能直接完成时直接调用；缺失部分由维护者补入既有工具，不安排一个常驻模型反复浏览页面。采集产生第3.4节的反馈待处理事项，原任务负责人在获准接续时读取并作科学处置。

部署时填入时间、时区、账号／项目、实际命令与宿主。具体接口尚待核实就明确为实现缺口，不能以“工具或 Agent 均可”替代选路。采集不自动唤醒主会话，也不自动批准、回复专家、返修或创建重复任务；若要定时启动任务负责人的语义处理，需要另外明确启动范围。本稿不启动任何自动化。

优先使用完整读取能力的受支持工具。页面读取时核分页、筛选、可见范围及错误；一次失败不等于没有新意见。先可靠保存成功取得的原记录及进度，再推进采集位置；分页或保存未完成时保留恢复位置，允许重读并去重。

以 review、意见身份及版本／内容指纹识别新增、修改、撤回和已处理项。重复采集不重复派工。未知历史起点先作有界初始对齐，不能假定历史意见都已结清。公开版本和发布变化也按声明交付回读；意见采集只覆盖已纳入范围的工作。

### 5.3 将意见对齐到准确数据

判断前定位意见对应的送审正文、当前线上完整正文、当前计划及本地工作体，比较相关依赖和实质差异。旧意见已被修订解决时关联具体变更，仍有效的意见保留。仅凭 UUID、最新文件名或意见摘要不能确定适用版本。

原任务负责人持续掌握背景，安排原执行者准备版本比较和必要证据，自己判断意见对用途、边界和进展的影响。常规反馈不转交新的常驻审阅者。复杂科学争议按第4.3节新建临时审查子 agent，传入实际争点、各方原意见和必要证据，其意见返回原负责人处理。

### 5.4 意见处置、审核建议和实际结果

| 意见处置语义 | 必要依据 | 后续 |
| --- | --- | --- |
| revise_data | 具体问题、证据、受影响内容及修改验收 | 在原任务安排返修，沿原审核退回与写责执行 |
| clarify_only | 数据可保留，但需解释、证据或用途澄清 | 准备有据回复；若需改正文则进入适用返修 |
| not_adopted_with_evidence | 原意见与事实、方法、物理关系、适用版本或本轮范围不符 | 保留原意见、反证、不采纳理由及数据自身合格依据 |
| needs_clarification | 意见含糊或证据冲突，尚不能稳健判断 | 提出精确问题，等待必要说明，独立工作继续 |

上述语义沿原意见记录表达，实际字段映射在实施时确定。整轮审核可保留 revise、recommend_accept、recommend_accept_with_non_adopted_comments 或 wait_for_evidence 等建议。它们是判断结果，不是新增看板状态或真实平台批准。

有据不采纳意见的接受建议，要求数据自身满足验收、相应意见有可核反证，且无未解决实质问题。保留专家原话、适用正文、判断者、理由和最终原生决定，不能删改原意见。“意见没有建设性”不证明数据合格。

重大科学争议由任务负责人派出的新审查子 agent 检查实际争点，使用第4.3节相同的独立输入、只读范围和返回方式，不复用原作者充当复核者。专家称谓、多数意见或模型自信不自动决定结论；普通措辞分歧无需重复全包审查。

### 5.5 回流原任务、执行处置并核结果

需要修订的意见进入原任务 todolist，继续关联同一发现、review 和责任人。已有事项直接更新；范围内返修不重新创建独立业务身份。任务负责人调整受影响计划，原执行者续做，未解决意见不会因新一轮开始而消失。

“需要修订”与“现在可写入”分别表达。state20 对象先经有权退回，完整回读实际 0 和可编辑条件后由原写者实施；此前维持 reviewing，允许只读分析和本地预案。公开数据沿适用后继草稿修订，模型派生对象从真实输入和模型修改。新 cycle 对应实质修订轮次，普通澄清、回复和重复采集不增加 cycle。

只需解释时准备回复，数据不重做；已经解决时引用证据结清本条；有据不采纳或仍有争议时保留相应处置。回复解决问题且无需修改数据时继续原审核。意见分类、建议通过、平台批准和实际发布分别保存事实。

具备明确权限与支持入口的责任账号执行适用退回、审核或发布动作并读回；否则留下准确待执行事项。作者不能凭不采纳意见冒充专家或管理员。对外发送回复需明确发送授权，准备回复不等于获准发出；已有覆盖当前动作的授权无需重复确认。

返修交接沿原任务引用 task/cycle、review 与送审体、原意见及处置、当前基线差异、修改要求、可复用材料、需重做的检查、实际退回结果和原写者。系统从已有记录组成接续信息，避免再手写一份完整返修包。

## 6. 知识、Skill、定期维护与递归改进

### 6.1 知识随使用积累，原件与关系各有职责

来源事实、模型选择、计算结果、研究认识和工作方法分别保留证据地位。原始材料与科学解释留原包；方法正文留原 Skill、工作流或代码。索引连接重要成果的输入版本、依据、用途条件、实际使用、反例和替代关系，帮助后续任务发现并核定可复用内容。

关系的来源是实际工作：专业包已有的输入与依赖直接读取；成果返回及采用决定提供产物和用途；方法调用提供实际版本；任务负责人或维护者只补工具无法表达但影响复用的条件、反例及替代判断。已有原生关系不再手工登记，缺失的重要跨任务关联补在同一 SQLite。普通笔记、每条交换和每次调用不强制成为独立知识对象。

研究认识由任务负责人沿原研究维护；共享方法、Skill 执行机制与工具知识由维护者承接。科研解释的实质改变仍回科学责任人。原件变化时，相关版本关系仍指向当时内容，新用途需核现版本的适用性；内容相同或路径相近不独自证明科学等价。候选、获准规则、已部署版本、实际使用与效果分别可查。

关联缺失、访问受限或索引未覆盖都明确显示覆盖范围，不解释成知识不存在。相冲突的适用判断同时呈现给当前责任人；检索排序、更新时间或文件名不替代科学判断。索引可按原件和真实记录重建，不能把重建索引当成重新作出历史采用决定。

### 6.2 能力发现与专业 Skill 进入实际行动

发现能力接在正常任务入口：第3.1节恢复目标和当前动作后，查询原包依赖、已有能力目录、知识关系及原生 Skill。优先提供与本次用途直接相关的现行方法、可复用资产、明确限制和关键反例，并显示来源及版本；详细原件按需展开。必要约束和适用冲突不能被摘要长度或排名静默丢弃，材料不全时指出待读取部分。这里复用现有查询与上下文组装能力，缺失部分补在原读取入口，不建第二个知识门户。

执行者开始新专业操作、遇阻、准备自建或改变用途时，沿这个入口作针对性查找。无命中先核检索覆盖，再查原工具说明、历史运行、真实数据与文件；已经适用的能力优先复用，不要求遍历全部目录。选用理由只有涉及重要取舍时才随原任务说明，普通工具调用不另写选择报告。

选用 Skill 后由实际执行者完整阅读主说明，沿本次用途执行必要分支。天工 AI 的检索、解析等能力用于发现和恢复证据，天工 LCA 的数据导入、Flow／Process 编制、Lifecycle Model 构建、求解、保存与发布按原专业入口执行。两者分别核实际部署、账号和权限，不因工具同属天工而假定输入、账号或回执可以互换。

已有 Task/attempt、检查点、next_actions 和专业回执是接续依据。执行者继续原检查点，将尚未完成的必要分支和阻塞原因随本次返回交回；任务负责人对照原用途与这些实际回执判断完成范围，必要独审检查其科学适用。工具已有强制检查直接使用；只有提示指引而没有机器证据的步骤，保留实际执行说明与原件，由负责人按影响核查，不能把读过 Skill 当成完成。

维护者根据真实失败定位能力未发现、Skill 分支漏执行、方法不适用或工具故障，修正具体发现或执行入口。各宿主必须能读取所选 Skill 并调用所需工具；接入不全时按第2.4节报告缺口。harness 引用专业状态机和回执，不另外编一套相同节点或要求执行者再次填写检查清单。

### 6.3 执行中交回发现，维护者集中诊断

执行者遇到有影响的工具、Skill 或 harness 问题时，随原返回明确指出问题、受影响用途、输入或证据位置、实际版本及临时处理。第3.2节接回入口将这项明确发现关联到原维护记录，并带上原任务和来源返回；已有同因事项直接引用，不复制正文。自由文本可能包含尚未识别的线索，但程序不凭措辞自动确认根因或宣称已登记全部问题。自动提取的疑似发现交维护者核定。

任务负责人处理科学影响、当前任务能否继续和研究优先级。维护者在自己的接续入口读取已委派范围的新增发现与未处置线索，无需研究主会话再手工转送一次，也不要求 worker 单独写经验报告或向主会话发消息。返回中明确有问题而维护关联未成功时，原返回保留待关联提示，重试同一关联即可；科研审阅可独立结清。

维护者核原输入、实际调用、版本、正常案例、已有办法和上游记录，区分使用错误、能力未被发现、规则未执行、方法不适用与共同实现缺陷。症状先作为观察，根因作为待验证判断；必要时安排针对性复现，不直接把模型的第一种解释交给工程修改。

同一机制的发现合并证据，不同组件与不同原因分别处理。维护者可以结清误报、采用现有办法、暂缓低价值事项或提出修订；处置保存在原发现，当前入口消费同一结论。发现数与 Issue 数不是改进成绩。原任务内已授权的普通科学修正继续就地完成，研究 worker 不顺手改共享代码、Skill 或正式评价规则。

### 6.4 定期维护与阻塞处理

常规共享问题由固定维护会话周期处理。每次维护 turn 从同一管理入口读取未结清发现、已关联上游事项和实际采用待观察项，通过获准的上游读取工具核有变化的 Issue、PR/MR 和版本，再诊断、合并、排序、提出具体修订或跟进已获准升级。原发现保存技术处置、上游链接和下一步，不另写一份维护进度日记。

有明确自动化授权后，复用现有调度入口按配置周期唤起该维护会话，完成一次处理即结束；启用前由用户进入同一维护会话发起。具体周期、宿主和启动范围是部署参数，本稿不设置新定时器。只读跟踪、提交 Issue、修改共享内容和部署更新按各自已有授权执行；定时触发本身不增加权限。维护可以以采用现有办法、有据暂缓或结清重复事项结束，不要求必须改代码。

影响关键推进的缺陷提前分诊；错误写入、版本混淆或错误采用风险先限制受影响操作并恢复事实，其他独立工作继续。提前分诊仍在当前获准接续内进行，不主动向主会话发送消息或唤醒。需要用户决定时在当前会话说明具体范围和依据，未获授权的外部动作保留为待审提案。

每次维护关注问题是否实际缓解、临时办法是否仍必要、同因是否复发，以及失效方法是否仍被推荐。已解决且无变化的事项退出默认关注；暂缓保留重启依据；上游未变且无新证据时不反复扩展调查或生产日志。

### 6.5 上游协作与受控版本更新

共享工程优先沿上游维护获得持久改进。维护者先查现成能力、已有 Issue 和正式修复；需新提问题时，讲清实际行为与影响、版本及复现依据、根因判断和不确定性、建议改法与理由。材料限于获准且必要的证据，不搬运完整科研包、凭证或无关日志。同因汇总到原 Issue，不同责任问题分别提出，集中处理不等于一个包罗所有问题的大工单。

上游保存工程讨论、PR/MR、检查和发布事实；本地沿原发现保存受影响任务、承接者、临时限制和实际采用，准确链接上游记录。修复优先交上游实施。需要本体系承担获准代码工作时，维护者按第2章配置派工程执行者，作者实施与自查、不递归分派；维护者另派非作者审查子 agent 核差异、必要验证和兼容性。上游正式审阅按其制度进行，本地预审不冒充上游批准。

候选先回原数据入口核其是否解决观察到的问题，按风险做必要检查；通过非作者预审、上游 PR/MR 与返修、正式发布后，再安排实际运行时采用。验证使用原问题的准确输入或有依据的等价输入；涉及真实写入时沿原授权，不为验证重放保存、送审或发布。工程状态和科研可用性分别承接。

维护者负责核发布版本、兼容变化、实际安装路径和所有受影响调用方的固定依赖，提出明确的升级范围与恢复办法。任务负责人判断当前研究适合在哪个接续点升级；已获准范围由维护执行者更新原安装与配置。总主不逐包重复审核升级，重大路线、权限或新的科学方法取舍才按责任交回。运行中的任务维持准确版本，不能静默替换依赖。

升级后经原调用入口读取实际版本，并在获准的原任务接续中使用。原执行者回报本次使用的版本、结果与残留问题；任务负责人核科学用途，维护者据此结清或保留待观察。直接 CLI 成功而 Foundry／Worker 仍调用旧版时，采用尚未完成；上游合并、版本发布、安装与真实效果分别保存原事实，不用同一个“已修复”覆盖。

实际使用失败时，先限制受影响调用，维护者核是否恢复原依赖／配置或采用已有临时办法；恢复保留新增成果与原回执，不以旧数据库覆盖新事实。新证据回原发现及必要的上游问题。harness 本身的缺陷同样沿诊断、具体提案、获准实施、独立工程审阅和实际效果处理，不因本仓库可写就跳过；已有批准范围无需层层重新确认。

### 6.6 RSI 的任务改进与递归改进

本设计把 RSI 理解为以实际工作证据持续改善方法，并改善选择、验证和采用这些方法的机制。沿此前对 Harness² 的讨论，保留提出候选、试探、组合与跨任务反馈的思想；本稿是适配本工作区的设计，不宣称复现该框架或获得其基准收益，也不依赖模型自动修改权重。

**第一层改进针对工作方法。** 发现来自失败、用户纠正、重复劳动、成功办法或新上游能力。任务负责人判断科学价值，维护者查共享原因、现成方法和可实施候选；执行者可以提出建议，但不承担未经委派的通用优化。候选沿原发现或原方法记录承接，引用旧方法、拟改位置、预期改善及适用范围，不另建重复的 RSI 工单。

需要比较时，维护者在原事项中明确基线与候选、可比输入与用途、需要观察的结果和已有授权下的投入，交合适执行者实施。候选与在用版本分开，优先复用已有离线运行、原工具版本或获准真实任务；结果留原运行产物，比较意见引用这些结果。普通缺陷修复做必要验证，主张方法泛化时才增加新工艺或未参与改进的输入，不给每个修复安排固定轮次和统一实验表。

有必要的科学独审由任务负责人安排，工程独审由维护者安排，已有适用审查直接消费。根据准确结果决定采用、组合、限定范围、继续补证或放弃；组合本身改变方法时也要核实际效果。工程候选走第6.5节上游协作；方法候选经获准审阅后修改原 Skill、研究方法或工作流，并将被替代规则从当前推荐中退出。正式科学规则、评价标准或适用边界的实质改变交科学责任人及必要独审，改进者不能通过改指标把失败写成成功。

**第二层改进针对改进机制自身。** 维护者在后续维护中沿方法的实际使用关系读取效果、成本、失败和反例，检查是否诊断表面化、漏找已有能力、重复生成候选、只记住原案例，或评价奖励了更多文档与操作。证据指向某个环节时，提出对原发现入口、检索选择、比较方法、评价或采用环节的具体修改；仍经同样的审阅、隔离试探与后续观察，不给改进者更高的自我授权。

例如，多个任务反复错过已有方法，先核是否为索引覆盖、用途匹配或 Skill 接续问题；若确需改善检索入口，就用已知漏检和未参与调整的适用任务检查找回及误用情况，再观察日常接续是否减少重复工作。原方法有效、新工艺失效时限制其范围或恢复旧方法，不把一次成功推广成全局规则。工具修好、增加预算、相似案例记忆与可迁移方法的收益分别判断，缺失工时和费用保持未知。

### 6.7 合并、退役与下一次使用

采用后的修改落在原规则或原实现，冲突旧指引同步修正；原发现关联正式方法版本、适用范围、关键反例和替代关系。维护者更新原能力目录或既有关系入口的推荐指向，正文仍只有一份。部署尚未完成的候选保持待采用，不让“已批准”提前进入默认运行。

下一次适用任务按第6.2节从正常接续入口取得现行方法，执行者核用途后调用；实际运行或返回自动关联所用版本，工具未提供的必要方法选择随原返回简要补充，不另写使用证明。原任务负责人判断成果是否满足用途，维护者沿使用关系读取后续效果。仅阅读、安装或运行成功各保留其事实，不能直接计作收益。

同因经验合并证据，条件不同的方法保留各自适用范围；失效或被替代方法退出当前推荐，旧版本和使用史仍可追溯。在途任务固定的旧版本不因索引推荐更新而改变。失败和反例回原方法及发现，真正改变适用判断时再打开有关待办；未变事项保持结清，持续无收益的候选收束。知识整理的目标是改善下一次选择和使用，不以文档数量或固定心得产量衡量。

## 7. 原生事实、可靠性与异常恢复

### 7.1 判断、工具事实和动作条件分别承接

现有 42 节点继续提供专业检查、合法结果、转移、失效及恢复规则，按当前动作展开。原生操作依适用合同执行，不将开放研究路线变成强制逐节点填表。任务负责人可以调整研究安排，实际平台动作仍核合法条件。

每项需要被后续消费的判断，应能定位具体问题及用途标准、准确输入与依赖、实际结论和理由、证据位置、覆盖与限制、下一步条件，以及实际判断者与时点。这些信息从原记录取得，只补当次必要缺口；不要求每个思考和普通动作都生成完整判断协议。

保留三层信息：原生事实说明工具实际做了什么及覆盖范围；解释性判断说明来源、科学含义和用途；当前动作条件说明本次身份、权限、前像、原 attempt 和检查是否成立。消费端核结构、来源、输入绑定、覆盖和适用转移规则，不能用模型填写的 success 冒充保存、批准或发布。

节点结果沿现有合法语义，至少能区分满足、不满足、证据不足和有据不适用。null、未读取、已读取为空及已证实不存在分别表达。只读 Adapter 按报告格式与版本提取事实，标明 unknown 和覆盖；旧报告原文保留，文件字节哈希与规范 JSON 哈希标清各自对象和计算口径。

### 7.2 共用异常规则

| 情况 | 处理与恢复 |
| --- | --- |
| 多人认领或同角色多任务 | 按准确任务、actor 和最新 revision 原子更新；只有成功者在授权内接续，原对象仍核单写者 |
| 原负责者退出或超时 | 原派发者先读宿主运行及原成果，核在途动作和副作用；能恢复则续原会话，确需更换才明确接替者；不凭租约到期接管或重放 |
| 当前正文或依赖变化 | 比较准确差异，复核受影响判断，保留未变有效依据 |
| 保存、提交、审核或发布结果未知 | 沿原请求和 attempt 查询实际效果，保留未知成员，避免另起请求猜结果 |
| 部分对象成功 | 保留逐成员结果与恢复点，仅处理未完成部分，按必要集合验收 |
| 新增共享依赖 | 查原身份、任务和写者，消费者关联同一成果，防止重复对象与重复研究 |
| 资料不足或旧报告覆盖不足 | 保留真实未知、适用假设与补证；只在实际用途需要时获取缺失当前事实 |
| 20 但专家不足或分配失效 | 保留实际状态和原 review，补足有效分配，避免重送 |
| 旧意见、意见错误或存在争议 | 对齐版本，保留原话和证据；按科学处置和真实审核权限接续 |
| 分页中断、重复采集或意见修改 | 按可靠采集位置恢复并去重，旧处置是否失效按变化范围判断 |
| 暂停、取消或被替代 | 接收指令的会话更新原任务受影响范围；派发者调用支持的停止入口并读取结果，未确认停止保持未知；不自动恢复，独立范围继续 |
| 工具或共享方法缺陷 | 留下原输入、错误、版本和返回点，接回入口关联原维护事项；维护者诊断并接上游，必要时限制受影响操作 |
| 跨宿主启动或返回中断 | 原派发者按请求查实际运行，沿原成果重接返回；启动不明时不重复启动，接回失败不重跑研究 |
| 用户纠正后旧执行返回 | 保存旧成果及其输入范围，对照最新计划判断可复用部分；不把旧返回直接采用为当前任务完成 |

用户在任一任务会话提出纠正或暂停时，接收会话先落实自己范围内的新要求，经原管理入口保存实际指令出处、受影响计划与运行关联。已有明确的新要求优先；跨任务影响留给相应负责人在获准接续中处理，不主动跨会话唤醒。原派发者继续运行时，通过宿主已有输入／中断能力通知自己派出的受影响执行，并取得接收或停止结果；无法确认时明确保留未确认状态，不以“已更新计划”代替执行已改变。

派发入口在启动或恢复前重读当前范围；实际保存、送审、发布等副作用入口在执行前核原授权、准确对象与当前计划是否仍适用。这里需要把检查接入真正使用的调用入口；未覆盖的直接调用须列为接入缺口，不能声称已被技术强制约束。普通读取与分析不逐步加审批。已发出的远端动作先查询实际结果，无法撤销时记录影响并由负责人决定后续。

迟到返回关联它实际使用的计划与输入，不覆盖新的决定。任务负责人核可复用成果、失效判断及真正需要返工的范围，再作当前用途决定；旧成果保留，无关成果继续采用。恢复或转交只补这一差异及未决操作，不要求重写完整交接报告。

历史报告较旧不自动意味着原动作 UNKNOWN，成功事实和原授权继续按其时点解释。新的用途或动作需哪些当前事实，再由原责任人取得。不能把未读到草稿等同于写入结果未知，也不能将历史 20 归一成 0。

原父子语义继续保持：D04 子修订完成返回父任务，不能提前关闭父删除任务；A13、B10 与 C01 沿各自声明目标验收。执行顺序和副作用依原合同，不由模型自由编造下一原生动作。

### 8.2 按实际依赖接通，不再建立平行系统

首先核目标运行环境的准确提交、SQLite 与原生对象位置、当前写入方、已绑定会话和可用接口。对拟采用的各模型／宿主组合，核启动、恢复、停止、结果读取、必要材料与 Skill／专业工具的实际可用性。没有运行端访问时保留未知，不凭 GitLab 源码推断生产部署，也不擅自克隆仓库、迁移主库或接管账号。

随后按以下依赖接通，具体代码与配置改动进入获准实施计划：

1. **任务与当前入口。** 复用原目标、brief、任务及 actor，生成第3.1节的不同职责视图；既有科学事实保持原位。确认总主能发现相关缺口、任务负责人能恢复完整背景与未处理事项。
2. **一次返回与处置。** 将原 CLI 接回、审阅和维护关联接到同一管理库，落实准确版本、真实身份、重复返回及失败恢复。已处理返回从当前待审中结清，同时停止对应多处手写更新。
3. **可配置派发与完整业务接续。** 按第2.4节接宿主原生运行能力，配置各职责的模型与工具范围；同宿主直接复用，跨宿主只补必要调用和结果适配。接通非作者子 agent 独审、返回与差异复核，核在真实副作用入口执行纠正与暂停条件。原生保存、送审和发布仍沿原写责。
4. **专业能力与知识使用。** 任务入口提供有关资产、方法、限制和反例，执行宿主实际读取 Skill 并接原检查点。原返回带回未完成分支和所用版本，负责人消费原专业证据，不增加并行检查台账。
5. **外部反馈、维护与方法采用。** 接通实际 review、意见、分配及发布读取，核版本对齐、去重与原任务返修；维护者接原发现及上游进展、运行时采用和方法效果。相关链路可用后，再按明确授权配置有限采集与维护周期。

每项接入都明确已有能力、实际缺口、原调用位置及需要停止的重复维护。已有接口足够时不另写适配；新增代码限于确实缺失的连接与检查，不默认新增守护服务、云端协调程序、可写看板库、独立知识库或实验平台。这是建设依赖，不是每个科研任务必须填写的五阶段流程。

### 8.3 兼容、版本与回退

实施使用明确获准的工作位置。原科学资产、准确方法版本、对象身份、授权历史和在途任务保留，已有负责人继续收尾。存储变更兼容增补；旧写入方不能覆盖不认识的新责任或决定，需适配或停止该写入入口，避免无保护双写。

上线保留受影响实现、配置及数据库的准确恢复点。回退恢复调用和读取方式，同时保留期间新增的科研成果、决定和授权事实；不能以旧数据库覆盖新工作，也不能借回退重放未知动作。索引可重建，原件与真实处置不可由缓存重写。

当前设计稿、实现检查、正式部署、实际使用和持续收益分别记实。部署后的进展在现有计划和本书状态中维护，不另建一份平行阶段台账。

### 8.4 验证范围与完成依据

历史回放用于核事实兼容和恢复，不重做已充分核验且未变的内容。新增实现做与风险相称的针对性验证，文档修订不运行代码测试。随后沿普通会话承担完整真实研究或数据修订任务，持续观察方向、交接与实际用途。

一个有界工作包能够提供局部证据，不能独自证明整体规模可用。验证任务由真实数据库需要选择，保留完整目标，不为展示闭环缩成单篇文献、单个字段或固定回合数。多个在管任务与实际同时运行数分别管理，依资源、上下文独立性和负责人负荷调整，不预设固定主审人数。

| 需要覆盖的情形 | 观察与核验重点 |
| --- | --- |
| 单过程、多过程服务与系统交付 | reference flow、参考方向与数量、连接、边界和本次交付分别成立 |
| 已有局部修订或用户中途纠正 | 保留原身份，受影响计划与后续动作改变，未变证据复用 |
| 局部 accepted、有限草稿或历史 20 | 科学覆盖和当前用途据实表达，不升级旧结论或改变历史状态 |
| 同角色多任务、原负责人退出 | 准确责任不混淆，恢复原任务与在途副作用，不自动接管 |
| 成果返回、应用中断或长期任务继续 | 普通入口找到准确成果，本次已处理返回能结清，不靠建设者中转 |

| 20 但专家不足、重复或失效 | 保留真实送审，补足适用分配，不重送 |
| 意见正确、含糊、无据或错误 | 分别形成具体修订、澄清或有据不采纳，保留数据自身验收 |
| 采集失败、分页中断、意见修改与撤回 | 可恢复、可去重，不丢意见、不重复派工 |
| 部分成功、UNKNOWN 或局部平台故障 | 保留逐成员结果，沿原 attempt 恢复，独立工作继续 |
| 批准未发布、发布后修订 | 区分真实阶段，保留公开版本与后继草稿关系 |
| 任务主审、审查子 agent 和总主接续 | 确认真实创建非作者子 agent，输入和返回绑定正确；负责人决定不冒充独审，返修只复核受影响部分，总主不默认重审 |
| 模型与宿主分工、跨环境材料访问 | 按角色配置取得实际运行身份，必要原件和专业工具可达，同一次返回能恢复且不重复派工；记录实际模型版本 |
| Skill 分支及方法真正复用 | 普通入口发现适用方法、限制与反例，实际执行原专业分支；未完成依赖随原返回承接，采用与后续效果回原方法 |
| 上游已修复但正式运行时未更新 | 维护事项保持实际状态，核安装、固定依赖及原入口采用 |
| 方法在原案例有效、新工艺失效 | 限制适用范围、补证或回退，反例回原方法 |

评价优先使用已有事实能支持的首次可用成果时间、原用途覆盖、影响用途的错误、返工与复发、等待传播、查找和重复维护负担、重复审阅、用户澄清与恢复投入，以及包含试探、失败重试和维护的成本。缺失工时和费用保持未知。不同模型的科学结论不要求措辞一致，但应能定位分歧依据；伪造证据、unknown 当通过、重复副作用或建议冒充实际结果应阻止相应动作。

### 8.5 原奶修订背景下的一次完整接续

以下用已有原奶修订背景说明目标工作方式，不宣称新协作链已经部署，不新增对该数据的科学结论，也不把该子项作为全框架验证任务。

总主在原任务、数据库相关质量报告与已有反馈中核定需要开展的完整修订范围，先确认哪些问题已经有人处理，再将目标、关键依据和边界写入原 brief，交稳定任务负责人。原奶是其中一个共享背景下的工作包，负责人按依赖安排相关来源、参考量、阶段边界或柴油数量的核查，不为每个字段或材料各配一位常驻主审。

负责人按角色配置派 worker。若采用拟核实的 ds4.1flash + Claude Code harness，派发入口使用已经验证的该宿主启动或恢复能力；GPT 负责人通过同一任务身份接回结果。worker 获得原包的可访问引用、所派范围、Skill 入口和返回位置；缺少原件或工具访问时先说明具体缺口。模型、宿主与账号的配置选择不改变专业要求或平台权限。

worker 从任务入口读取适用方法和关键反例，沿原 Task/attempt 完成必要专业步骤与自查，保存准确修订体、差异和检查依据。接回入口核原件后保存本次返回。负责人按原用途及检查变化安排独立审查子 agent；其模型与宿主从科学审查配置取得，不因它也是子 agent 就自动沿用生产 worker 的模型。

审查子 agent 读取实际候选、来源和必要计算，判断所派科学问题，沿原请求返回。任务负责人据此核计划覆盖、用途和下一步，不替作者重算。需返修则回原 worker，再由原审查子 agent 核变化；采用或返修决定保存一次，当前入口结清已处理范围。总主在正常接续中消费该完整任务的贡献和例外，无需再逐项检查原奶计算。

期间若用户纠正用途，接收会话先落实受影响工作，原派发者按第7.2节更新在途输入或停止相关执行。已有结果按准确版本保留，迟到成果由负责人判断可用部分，不重新启动整批研究。若发现读取工具漏字段，worker 在原返回中留下观察、版本与影响，接回入口关联维护事项；数据审阅可以结清，工具问题继续由维护者承担。

维护者核根因与已有上游修复，必要时提出获准的 Issue，跟进原入口验证、工程预审、PR/MR、发布和实际依赖更新。任务负责人选择适当接续点，原 worker 使用新版本并交回效果；修复无效时沿原问题处理或恢复旧调用。需要改进的是发现方法或 Skill 接续时，候选沿原事项比较，获准后修订原方法入口，下次任务实际使用再反馈效果。

合格数据沿原写责保存、完整读回、送审并完成适用专家分配。新增意见由有限作业采集、对齐版本并进入原任务，负责人决定修订、解释、已有解决或有据不采纳。需要改正文时先取得适用退回和可编辑状态，再由原 worker 接续。意见处置、科研采用、工程修复和实际发布各沿原记录保持其含义。

这条接续路径使用同一原任务、原专业包及准确请求关系。稳定背景只维护在原计划，动态事实由原工具提供，负责人只补需要判断的变化；具体运行身份、版本和返回关联由入口取得，参与者不再各写一套交接材料。
